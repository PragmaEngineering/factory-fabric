# Shared agent assignment contract

## Audit (FAB-012)

Controls already owns authenticated participants, thread membership, durable messages,
receipts, session supervision, and Factory result effects. These remain authoritative.
Fabric's registry already supports leased connected implementations; it must not be
replaced by a second registry. Factory's runner already binds input/configuration
and selects a native adapter. Reuse these boundaries.

The current incompatibilities are at the process/agent boundary:

| Concern | Factory today | Fabric today | Target |
| --- | --- | --- | --- |
| Assignment | input/config/prompt files | staged input/config/context files | authenticated MCP lookup |
| Connection | FACTORY_MCP_* variables | FABRIC_CONTEXT_PATH document | endpoint + participant credential only |
| Result | SDK discovers controller; step_result | fabric.result to configured peer | assignment_complete |
| Runtime | adapter selected from YAML | raw command only | explicit YAML protocol/runtime selection |
| Native profile | prepared by Controls | implicit launcher defaults | YAML settings applied by runtime |
| State | workflow result/effect | invocation result/state | common receipt; owner interprets result |

`task-readiness/run.mjs` requires Factory runtime variables before calling its
reusable evaluator. `result-client.mjs` assumes a controller-kind participant.
`pi-rpc-session.mjs` assumes workflow-specific completion and runtime-status
payloads. Fix those shared boundaries; do not fork each agent implementation.

Provider keys remain deployment secrets referenced by YAML. They are not sent in
assignment documents or model prompts. Project files remain on the execution host.
No workflow engine, new identity system, message broker, or implicit package sync.

## Implementation sequence

1. Audit and record reuse boundaries.
2. Specify the authenticated MCP assignment operations and durable retry semantics.
3. Make protocol/runtime bootstrap an explicit package setting in YAML.
4. Implement the shared Controls operations, SDK, and Factory/Fabric producers.
5. Migrate readiness and prove both producers use the same implementation.
6. Migrate the shared Pi adapter; update skill, discovery, operation docs and tests.

## Version 1 MCP contract (FAB-013)

Bootstrap consists only of `AGENT_MCP_URL` and `AGENT_MCP_TOKEN`, generated by the
launcher from the existing scoped participant registration. These are connection
configuration, not operator-maintained assignment variables. A connected program
can supply the same values through its own MCP client configuration. Never pass
service-admin credentials to workers. Legacy files/variables require the explicit
`protocol: legacy` compatibility mode; `protocol: mcp` is the new package mode.

Controls' existing communication MCP endpoint adds:

- `assignment_get({id?})`: fetch the authenticated participant's assignment. With
  no ID, select its current assignment. A supplied mismatched ID is rejected.
  Return version, ID, capability contract, input, configuration (secret references
  only), instructions, thread/participant IDs, execution-host working/files
  directories, state, and optional output/error. No peer can read another assignment.
- `assignment_status({id?, state?, message?})`: inspect status, or report running
  or waiting with an optional explanation. It does not route workflows or finish work.
- `assignment_complete({id?, output?, error?})`: exactly one output or nonempty
  error. Validate output against the pinned schema before accepting it. Return
  `{assignment_id, state:"accepted", receipt}` only after durable communication
  acceptance. Unchanged retries recover the same receipt; changed completion is
  rejected even if the caller invents another operation ID. Status reports cannot
  overwrite terminal completion.

The host provisions an immutable assignment through the trusted host API before
launch. Identity and thread membership come from existing comms registration.
One supervised invocation owns one assignment; connected capability registration
and renewable mailbox leases remain Fabric's existing API. No new worker queue.

The common completion operation hides the owner-specific result effect. Factory
maps its output to the existing validated step result (or a failed result);
Fabric maps output/error to its existing pinned invocation. Internal message kinds
can remain compatible during migration, but agents never need to choose them or
discover a controller participant. The existing message API remains available for
peer communication and bounded waiting.

Factory workflow metadata is optional owner metadata. Neither execution/step IDs,
workflow routes, outcome branching, publication bookkeeping, nor artifact digests
are required to connect a Fabric implementation. File paths refer to actual work
on the execution host; assignment delivery itself never requires shared files.

### Native runtime and migration boundary

`runtime: {name: pi, version: '=1.0.3'}` and `protocol: mcp` select supported native
preparation in YAML. Existing package provider overrides are applied by that
preparer, not reimplemented in each registry agent. `environment` remains the
explicit execution-host secret-reference mapping. Connected implementations keep
registering through the existing Fabric lease API. Their mailbox dispatch remains
supported while supervised packages move to assignment MCP.

Legacy Factory packages retain their current behavior. The common MCP contract
is additive; old completion payloads remain compatibility internals. Mark an
implementation runnable only for the protocol/runtime combinations the host can
actually prepare. Do not relaunch an uncertain invocation during this migration.
